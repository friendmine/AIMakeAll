# Linux From Scratch 知识体系与项目接入

更新：2026-11-17。本模块以 [LFS 13.1-systemd](https://www.linuxfromscratch.org/lfs/view/13.1-systemd/) 为章节基准，覆盖前言、11 章和附录 A–D。该版发布于 2026-09-01；固定版本页面作为学习入口，避免随 `stable` 别名变化混用包版本或步骤。**当前完成知识映射与实验设计，尚未构建 LFS、创建虚拟机或启动 Linux guest。**

LFS 补上 AIMakeAll 的操作系统构建线：从已有 Linux 构建环境出发，理解工具链如何自举、基础用户态如何形成、内核如何启动以及服务如何运行。它主要组装和编译已有开源软件，不等同于自己编写一个内核。[LFS 项目介绍](https://www.linuxfromscratch.org/lfs/)

## 1. 与现有学习体系的关系

系统机制由 [OSTEP 模块](OSTEP_FOUNDATIONS.md) 补足调度、页表、同步和持久化；LFS 实验继续负责从源码组装、配置与启动。先做小型原理实验，再将其用于 Linux 运行时和驱动。

| 学习线 | 关注的问题 | 项目交付方向 |
| --- | --- | --- |
| [CSAPP](CSAPP_FOUNDATIONS.md) | 程序与系统如何工作 | 链接、异常、内存、进程、I/O 与网络原理 |
| LFS | 如何从源码构建可启动的 Linux | 工具链、根文件系统、内核、启动配置与系统维护 |
| [UDL](UDL_FOUNDATIONS.md) | 模型如何学习和泛化 | 模型结构、优化、训练与质量评估 |
| [MiniMind](MINIMIND_INTEGRATION.md) | 完整 LLM 实现如何组织 | 预训练、SFT、推理和工具调用参考 |
| RISC-V + NPU + QEMU | 模型算子如何执行 | 裸机驱动、模拟设备、运行时及后续 Linux 后端 |

项目继续先做 Ibex RV32IMC 裸机与 INT8 NPU。LFS 基础实验可以并行学习；**RV64 Linux 是单独的系统扩展**，不作为首版 M1/M2 的前置条件，也不表示 Ibex 获得了运行常规 Linux 所需的平台能力。

## 3. 工具链与依赖的核心认识

### 从已有系统到新系统

学习路径为：已有 Linux 和编译器 → 临时工具链 → 临时用户态 → chroot 中的最终系统 → 新内核启动。前几步借用构建机内核；只有启动目标内核后，才完成独立运行验证。

LFS 使用交叉编译方法减少对宿主环境的依赖，即使最终仍在同一机器架构上运行。官方明确说明其步骤不是通用交叉工具链教程，不能直接拿来生成任意目标的工具链。[工具链说明](https://www.linuxfromscratch.org/lfs/view/13.1-systemd/partintro/toolchaintechnotes.html)

在工具链术语中，build 是执行构建的系统，host 是构建出的工具运行的系统，target 是编译器生成代码面向的系统。这与“macOS 宿主机 / Linux guest”的虚拟机称呼不是同一个层次，实验记录应分别填写。

### 按职责理解软件依赖

| 软件类别 | 需要解释的依赖关系 | 与 AIMakeAll 的连接 |
| --- | --- | --- |
| 汇编器、链接器与编译器 | 编译器需要目标头文件和运行库，运行库本身也要被构建 | CS03/CS07；RISC-V ELF、ABI 与链接脚本 |
| 内核 API 头文件与 libc | 用户态调用接口、动态加载器和 C 运行库相互配合 | C 推理程序、文件加载与系统调用 |
| shell、文本与构建工具 | 构建脚本依赖可用的命令、解释器和生成工具 | 可重现构建、日志解析与错误定位 |
| 文件系统、设备与 init | 挂载、设备节点、权限、内核模块和服务启动有先后关系 | 后续 NPU 驱动节点、模型目录与服务依赖 |
| 软件包记录与更新 | 安装成功之外还要知道文件归属、配置及依赖变化 | 镜像清单、回退点、升级后的数值与启动回归 |

已有 RISC-V 裸机 GCC 不自动等于 Linux 用户态工具链；目标 libc、动态加载器、ISA/ABI 必须重新核验。LFS 基础系统也不自动包含完整的 PyTorch、MiniMind 依赖或本项目 NPU 驱动。

## 4. 本机学习环境与版本边界

官方主目标是 x86/x86-64；其他架构需要调整。本项目的基准复现选择 **Linux x86-64 构建环境及同架构目标**，以便与书中流程对照。RISC-V 路线另建适配记录。[架构说明](https://www.linuxfromscratch.org/lfs/view/13.1-systemd/prologue/architecture.html)

| 环境 | 本项目安排 | 验收边界 |
| --- | --- | --- |
| 当前 Apple Silicon macOS | 编辑文档、管理源码和构建日志 | Homebrew/Nix 工具齐全也不等于满足 Linux 内核与 chroot 条件 |
| Linux x86-64 实验环境 | 作为 LFS 基准复现环境，可运行在独立机器或完整模拟环境中 | 在 Apple Silicon 上跨 ISA 全系统模拟需实测时间，不承诺原生构建速度 |
| Linux ARM64 虚拟机 | 可选的适配研究或后续交叉构建环境 | ABI、包补丁与引导均单独验收，不能标为原样复现 x86-64 流程 |
| RV64 QEMU Linux guest | 后续 AI 系统运行目标 | 独立内核、固件、rootfs 和设备模型；不是 x86-64 镜像转换格式即可启动 |

LFS 13.1-systemd 的宿主要求页建议至少 4 核、8 GB 内存，并列出工具版本和链接要求；这些是书籍建议，不是本机性能保证。实际构建前在选定的 Linux 环境执行该版检查，结合磁盘空间与阶段备份确定资源预算。[宿主要求](https://www.linuxfromscratch.org/lfs/view/13.1-systemd/chapter02/hostreqs.html)

实验使用专用虚拟磁盘和 Linux 文件系统；macOS 共享目录仅用于交换源码/结果，不默认承载需要 Linux 所有权、设备节点和挂载语义的根文件系统。环境修改限定在实验虚拟机内，保持现有 EDA/OpenRAM 与模型环境独立。

选择 systemd 版是为了后续服务生命周期学习。SysVinit 可作为对照选修，但不混用两版启动章节和包集合。当前只固定教材基准，没有锁定下载包、QEMU 或虚拟机镜像；真正构建时还要记录勘误、必要补丁、来源哈希和许可证，不能用版本号代替完整构建记录。[勘误入口](https://www.linuxfromscratch.org/lfs/view/13.1-systemd/prologue/errata.html)

## 5. 迁移到 RISC-V 与 QEMU

### 两条执行路线

| 路线 | 目标 | 用户态/设备访问 | 定位 |
| --- | --- | --- | --- |
| RV32 裸机 + NPU | 现有 M1/M2 主线 | 固件直接按板级协议操作 MMIO，静态内存预算 | 先完成最小硬件功能闭环 |
| RV64 Linux + NPU | 后续系统扩展 | 用户进程通过内核驱动和受控接口提交算子 | 承载文件系统、进程、网络及推理服务 |

RV64 扩展计划采用 QEMU `virt` 学习 Linux 启动。该平台由 QEMU 提供，具有设备树与虚拟设备，不能用它的运行结果证明 Ibex SoC 已能运行 Linux。QEMU 官方提供 OpenSBI 加内核的启动方式；具体固件、内核配置、命令行、rootfs 与 QEMU 版本须一起固定。[RISC-V 系统说明](https://www.qemu.org/docs/master/system/target-riscv.html) · [virt 平台](https://www.qemu.org/docs/master/system/riscv/virt.html)

项目迁移顺序如下，均为待实现的扩展任务：

1. **启动诊断**：先准备 RV64 Linux 内核和极小 initramfs，串口启动到命令行；这一检查不计为完整 LFS 构建。
2. **根文件系统**：把 LFS 的分阶段构建方法迁移到 RV64，记录工具链、libc、包补丁和引导差异，再完成磁盘 rootfs 与冷启动。x86 的 GRUB 配方不直接套到 RISC-V。
3. **设备接入**：为自定义 NPU 增加 Linux 可识别的设备描述与驱动，单独定义用户态接口。裸机指针读写不能直接搬到 Linux 普通进程。
4. **内存与算子**：由驱动管理缓冲区、地址转换、完成通知及错误回收；区分用户虚拟地址、guest 物理地址和模拟器宿主地址。对照 [NPU 语义](../specs/npu-v0.md)，核验 RV64 地址宽度与现有寄存器草案的兼容范围。
5. **模型与服务**：先运行 C 数值基线，再运行量化模型，最后将推理和受限工具作为服务启动，加入并发、超时、停止及重启测试。

共用的是 GEMM 数值语义和测试向量；RV32/RV64、裸机/Linux 的二进制与驱动层分别构建。Linux 启动成功、NPU 可用、模型质量和 Agent 成功率分别验收。

## 6. LFS 之后的 AI 系统

[Beyond Linux From Scratch](https://www.linuxfromscratch.org/blfs/) 提供基础系统之后的软件安装与配置参考。本项目只按需要引入通信、证书、调试和服务依赖；BLFS 全部内容不作为必修。

最终扩展目标是：Linux 启动 → 文件系统和设备就绪 → NPU 驱动就绪 → C 推理服务 → Agent 工具服务。服务通过普通账户运行，明确模型只读目录、可写日志、请求限制与退出行为；先验证单请求，再增加并发和资源管理。

训练保持在宿主计算环境中，导出的权重与运行时进入 guest。将整个 MiniMind/PyTorch 训练栈搬进自建 Linux 是额外工程，不作为 LFS 学习或首版 NPU 推理验收条件。系统服务管理不会自动提高模型能力，也不会使 QEMU 功能模拟变成周期精确仿真。
