# 公司训练场景（历史方案）

本页保留早期组织训练方案。当前课程目标和毕业条件见[个人培养规划](CHIP_MODEL_PLAN.md#个人毕业任务)。

此方案用一款共同开发的 AI 处理器演练从选择客户问题到维护产品的完整过程。全员要能解释客户买什么、产品如何工作、公司用什么证据作出承诺。每个人还要深入一个岗位，完成一份能被下游实际使用的交付物。

首轮按**无晶圆厂（Fabless）AI 芯片设计公司**组织。公司负责产品定义、芯片与软件设计、验证、供应商协同和客户交付；晶圆制造与封装测试作为合作方接口进入训练。共同产品是一套开源 RISC-V + 数字 NPU 推理系统，负载是自训练的小 Transformer，应用验收使用受限工具 Agent。数字电路和模型双向迭代的实验方法见[芯模协同设计规划](CHIP_MODEL_PLAN.md)。

## 先上哪一课

模拟客户打算在受限缓冲预算下部署模型，要求团队回答“能运行吗、质量达标吗、交付时能承诺什么”。产品、芯片、软件、模型、验证和客户支持共同评审两份已经保存的报告。参与者可以直接读表，工程人员还可以用 Python 重放。主持人手册包含需求卡、分工、可核对的答案和交接记录。[第一次跨岗位评审](../labs/01-linear257/product-review.md)

之后按岗位分流。业务岗沿着需求、成本、客户试用和发布走一遍。研发岗沿着模型、架构、RTL、软件和验证走一遍。制造运营岗沿着设计交付、封装测试、良率和质量反馈走一遍。三条路线在架构取舍、版本发布和客户问题复盘时汇合。

## 岗位知识与交接

| 岗位和判断 | 岗位实验与交付物 | 接收方怎样验收 |
| --- | --- | --- |
| 战略、市场与产品：选哪类客户，替代方案是什么？ | 为边缘推理场景写一页产品需求。给出代表负载、CPU 替代方案、成功指标、可接受成本和失去此客户的条件 | 架构能据此写工作负载，销售与现场应用工程师（FAE）能将其改写成客户试用条件 |
| 系统与芯片架构：预算花在阵列还是存储？ | 从提示词处理和逐 token 生成各取一组张量，分解算力、片上容量与带宽；冻结数值语义和寄存器接口 | RTL、编译器和验证使用同一版本独立算出相同形状、地址范围和预期结果 |
| 算法、模型与数据：允许多少质量退化？ | 训练浮点基线，登记数据来源、划分与检查点。交真实张量、量化尺度和留出集结果；按硬件瓶颈再训一个候选模型 | 编译器可加载，验证能分开判断实现误差、量化误差和模型结构变化 |
| 数字前端、IP 与 SoC：设计怎样实现并复用？ | 交付可综合阵列、局部存储与控制 RTL、接口时序、复位和背压行为，接入 RISC-V；说明第三方 IP 版本和边界 | 验证能注入停顿与复位，固件能提交事务，后端能取得可综合顶层及约束 |
| 验证与性能：什么证据支持设计决定？ | 建独立参考、需求与用例对照、断言、失败重放和同负载性能对比；给出未覆盖场景 | 架构能从波形找到瓶颈，质量负责人能从需求追到通过或失败的原始结果 |
| 物理实现、供电与可测试性设计（DFT）：何处可能影响时序、面积和可测性？ | 在选定开放库上对小模块做综合、布局布线和静态时序分析，读关键路径；用教学故障集做扫描链或存储测试练习 | 前端能据报告修改一条路径，测试工程师能说明哪些故障可检出、哪些尚未覆盖 |
| 固件、编译器、运行时与 SDK：客户代码如何用上 NPU？ | 交裸机驱动、模型包、CPU 回退、示例、兼容矩阵与错误诊断；同一命令分别在 QEMU 和 RTL 上检查 | 模型团队能导出，FAE 能从干净环境运行示例、复现坏包或版本错误并回退 |
| 板级、封装、测试、供应链与量产运营：怎样交付可用产品？ | 用假设的封装引脚、电源与热预算编制系统集成和首次上电计划；用模拟晶圆测试、封装终测分档与交期数据估算可交付良品 | 系统团队能标出电源/复位假设，采购能指出瓶颈与备选方案，质量能追溯异常批次。每份报告标明仿真、估算或待硅后实测 |
| 工程基础设施、安全、知识产权与质量：团队能否重建、授权和修复这一版？ | 固定工具/IP/数据与权重版本，生成依赖及许可清单，跑回归；演练一次组件升级、权限拒绝和版本回退 | 发布负责人从版本清单重建产物，能定位受影响组件并明确修复和复验责任 |
| 项目管理、财务与经营：怎样决定投钱、延期、缩减规格或停止？ | 建人力、EDA/IP、一次性投入、单位成本、需求量与进度假设表；用一项规格变更重算账期、关键路径和盈亏平衡量 | 管理评审能在相同销量与良率假设下比较方案，知道哪个假设改变会推翻决定 |
| 销售、生态、FAE 与售后：客户能否用起来，问题如何回到下一版？ | 给出产品简报、开发者示例、试用验收单和已知限制。用客户工单复现故障、提供临时方案、修复并回归 | 客户角色用自己的输入复测，产品把差异写回需求，供应链或研发能按证据判断归属 |
| 组织与人才：关键工作由谁承担、如何传承？ | 为本次发布画出责任分工、关键岗位备份、培训顺序与交接清单。让未参与原实现的同事接手一次故障 | 接手人能找到版本、责任人和复现入口，复盘能具体指出缺少的知识、资源或人员安排 |

十八个技术领域给各岗位提供知识入口，岗位实验要求接收方真正使用产物。技术资料沿用[课程目录](CURRICULUM.md)、[知识覆盖索引](KNOWLEDGE_COVERAGE.md)、[芯片物理与产品流程](CHIP_AI_COMPLETENESS.md#chip-物理实现与产品流程)及[来源与许可清单](OPEN_SOURCE.md)。

## 一款产品的六次评审

| 评审与牵头人 | 本轮必须做的决定 | 输入、交付与通过条件 |
| --- | --- | --- |
| 立项 · 产品与经营 | 这个客户场景值得投入吗？ | 比较 CPU 方案与教学 NPU，交需求卡、预计成本和停止条件。至少一条用户需求能被独立测量 |
| 规格 · 系统架构 | 哪些模型算子进硬件，哪些留在 CPU？ | 用同一模型层冻结精度、布局、内存、性能与质量预算，交硬件/软件接口和验收向量；下游能独立解释契约 |
| 原型 · RTL、模型与软件 | 数值已对齐吗，主要瓶颈在哪里？ | 复用 M1/M2/M3 的真实张量、寄存器轨迹、波形与质量报告。依芯模联合实验决定改硬件还是改模型，保留落选理由 |
| 设计交付与量产准备演练 · 后端、测试与运营 | 哪些项可交给制造伙伴评估？良率或交期变化会怎样影响订单？ | 交小模块物理报告、测试程序思路、假设批次的良率与成本表、待硅后验证清单。标注单位、数据来源和适用范围 |
| 产品发布与客户导入 · SDK、质量与 FAE | 哪个客户场景可以试用？对外可以承诺什么？ | 交版本化发布包、安装示例、已知限制、支持与回退办法。接收方在干净环境完成客户用例，每项对外指标可追溯到对应负载和证据 |
| 现场复盘与下一版 · 客户支持与产品 | 工单应由软件、模型、硬件还是供应商解决？下一版是否立项？ | 重放现场输入，交原因、临时解决办法、修复回归和客户复验；把新增边界用例、成本影响及客户接受条件写回下一轮立项 |

贯穿六次评审的是同一份产品档案。每个小组保存需求与版本、设计选择、度量口径、原始证据、未决问题、负责人和下游验收人。规格发生变化时，先定位哪些测试、成本和客户承诺需要重验。教学制造数据可从小批次的假设开始，例如要求交付 1,000 颗良品，让运营按探针测试与封装终测两段良率倒推投料量，再由财务检查每颗良品的成本。真实良率、交期、商业价格和硅后性能须由相应的实际数据支持。

## 如何组织训练和考核

| 训练层次 | 个人或团队需要做什么 | 通过条件 |
| --- | --- | --- |
| 全员共同课 | 在首次评审中解释客户任务、跟踪一项需求，说明芯片、模型、SDK 和成本各如何影响它 | 能引用正确版本，也能指出一项证据不足的产品承诺 |
| 岗位深修 | 选上表一个岗位，完成一份带输入、原始证据和失败样例的专业交付 | 下游能按约定接收标准独立使用；退回时有具体原因和补验结果 |
| 跨岗位轮训 | 到相邻岗位担任接收人，处理一次预算变化、模型包不兼容或假设良率下滑 | 能追溯变更影响，给出修改、延期、限量试用或停止的有据决定 |
| 团队毕业 | 从客户需求走到发布，以及一张工单的复验。汇集技术指标、模型质量、成本与支持承诺 | 换组重放关键结论，客户角色验收应用任务，团队说明待测项与下一版优先级 |

一个人可以轮换角色完成同一套档案，把自评与他人复核分别登记。小组可以兼岗，由另一位成员接收交付物；跨团队训练则让产品、研发、运营、客户角色分别承担评审。岗位能力、跨岗交接和整个产品的结果分别登记，便于判断具体要补哪一课。

## 从现有仓库开始实施

1. **现在开展首次共修。** 用已有的 257 项 Linear 和两份预算报告完成跨岗评审。技术数值已有本机证据，团队讨论情况和学习结果由参与者实际登记。
2. **随芯模工程开展岗位实作。** 阵列、存储和模型训练分别产出各岗位的第一份交付。在已训练层进入 RTL 时开展规格和原型联合评审，沿用原 M0–M4 里程碑。[技术实施阶段](ROADMAP.md)
3. **用同一版本演练商业交付。** 增补 SDK 候选包、教学测试与良率数据、成本场景和客户工单，开展发布、回退与下一版决策。物理实现与制造按仿真或案例标记。当前这些演练处于规划阶段，需分别交付材料、运行和真人验收。
