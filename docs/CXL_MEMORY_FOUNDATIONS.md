# CXL 与异构内存：从 Type 3 扩容到模型内存放置

[相应系统实验、命令与本机验证记录](EXPERIMENTS_09_23.md)

更新：2026-11-17。CX01–CX06 为本项目原创模块编号，已有实验 23 的静态 Type 3 窗口、地址读写及权重/KV 放置样例，完整专题按下表各项验收。安排在 [S3](ROADMAP.md)：先掌握 PCI/PCIe 枚举、Linux 地址空间与内存生命周期，再进入 CXL；不阻塞首版 NPU、模型或 Agent。

## 定位与协议边界

CXL 与 PCIe 共享许多基础设施，增加面向内存和一致性的机制。学习时区分 CXL.io（I/O）、CXL.cache（设备一致性访问主机内存）、CXL.mem（主机访问设备内存）。并非所有设备支持全部协议。

以 CXL 2.0 的常见设备分类作为入门框架：Type 1 使用 CXL.io/cache；Type 2 使用 io/cache/mem；Type 3 使用 io/mem，作为内存扩展起点。Type 3 可以提供易失或持久内存，但“CXL 内存”本身不等于“持久化完成”。后续版本与功能须按选定版本重新核验。[QEMU CXL 设备分类与范围](https://www.qemu.org/docs/master/system/devices/cxl.html)

本课程第一条可执行路线是单主机、静态拓扑、Type 3 易失内存。多主机共享、内存池/fabric 管理、Type 2 NPU 和真实一致性 RTL 属于后续研究，不把它们包装成首个实验能力。

## 知识与实验

按 [仿真优先原则](SIMULATION_FIRST.md)，系统线使用 QEMU Type 3，数字线补 CX-H1 简化内存事务参考模型、CX-H2 译码/请求响应队列/存储访问 RTL。测试台注入背压、边界和复位，输出波形与综合网表；接口为原创教学子集，不宣称完整 CXL.mem 控制器。CX06 的一致性从有限状态模型与断言开始，实物 CXL 内存不是验收前提。

| 模块 | 知识范围 | 原创实验与产物 | 验收门槛 |
| --- | --- | --- | --- |
| CX01 一致性与设备类型 | cache coherence 与 memory consistency 区别；io/cache/mem、Type 1/2/3 | 画出 CPU、缓存、主存、设备内存及协议路径，建立能力表 | 能区分设备 DMA、主机访问扩展内存与一致性访问；每项能力标注来源和版本 |
| CX02 发现与地址译码 | Host Bridge/Port、ACPI CEDT、固定内存窗口、HDM Decoder、HPA/DPA | 在独立 QEMU/Linux 环境发现单个 Type 3，记录地址窗口与设备拓扑 | 固定版本可重复启动，解释主机地址与设备地址映射；发现设备不算内存已经可用 |
| CX03 Linux 内存使用 | region、DAX、system RAM、内存上线、容量与生命周期 | 在一次性 guest 中创建内存 region，选择 DAX 映射或 system RAM 路径并读写校验 | 分别证明区域配置、应用可访问和数据正确；记录容量变化；切换路径前释放使用者 |

| CX06 高级扩展 | 交错、多设备、热插拔、持久性、RAS；Type 2 一致性原理 | 在隔离 guest 中做拓扑/故障实验；另建一致性有限状态模型、断言及选定子集 RTL；持久内存另写恢复协议 | 状态/数据不变量与公平性假设明确；综合范围可追溯；不得从 Type 3 或教学模型推断完整 Type 2/多主机合规 |

## 首个贯通实验：单 Type 3 内存区域

1. 固定 QEMU、Linux、固件和用户态管理工具版本，建立独立 x86-64 `q35` 实验 guest，按上游示例审查窗口、端口和内存后端。先验证官方目标组合；不假定现有 RV64 `virt` 配置能直接复用 CXL。
2. 保存启动日志和拓扑，确认设备被识别，再配置并核对 region、decoder 和地址范围。
3. 首先选择一种内存呈现方式：DAX 应用映射或 system RAM；另一种作为对照实验，转换前释放映射并按选定内核/工具流程操作。
4. 用固定种子在已确认的区域写入/读取合成张量，覆盖边界和容量不足；保存访问方式与地址范围证据。
5. 接 CPU 模型前先做容量账本，区分权重、激活、KV Cache 与运行时开销。QEMU 数值结果和配置可用于功能验收，硬件性能留待真实平台测量。

交付计划：版本与配置、拓扑/地址图、发现与 region 证据、应用校验程序、内存放置与容量报告。当前未构建 guest、配置内存区域或运行上述实验。

## 与现有 NPU、编译器的连接

CX-H2 的译码/队列使用 [DD](DIGITAL_DESIGN_TIMING.md) 方法；CX06 状态模型按 [DV03/DV05](SYSTEMATIC_VERIFICATION.md) 写安全性质、可达性及活性前提；容量/延迟模型按 [SIM05–SIM07](SIMULATION_CREDIBILITY.md) 做独立校验、敏感性与不确定性说明。教学状态模型证明不等同于完整 CXL.cache/CXL.mem 标准合规。

当前 NPU v0 的 32 位设备地址不能自动覆盖任意 CXL 地址区域。CX05 先在 CPU 路径使用扩展内存；未来 NPU 要么通过明确的可寻址暂存区搬运，要么增加经过验证的地址映射/新 ABI，并检查 DMA/IOMMU 与平台访问支持。不能只把权重放入 CXL 就声称 NPU 已接入。

[AI 编译](AI_COMPILATION.md) 后续可输出张量生命周期与内存类别提示；运行时负责实际放置、暂存/迁移与失败回退，必须报告新增搬运和同步开销。NUMA 或 CXL 并不自动提高 tokens/s。

QEMU 文档明确其相关功能模拟不模拟完整缓存一致性协议；不能据此验证 Type 2 一致性时序或推导真实 CXL 带宽、时延。初期成本曲线只标“参数化估算”，不伪装成实测。[QEMU 模拟边界](https://www.qemu.org/docs/master/system/devices/cxl.html)
