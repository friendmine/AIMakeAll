# 实验 04 · 独立试读任务单

适合能读 C 循环、知道矩阵行列、会在终端运行 make 的学习者。目标是独立判断一次加速是否值得，并用真实记录说清原因。请从项目首页寻找实验入口。用全新的检出目录或记录复用的检查点、缓存和工具。下面的表供实际参与者填写，当前试读状态为**待执行**。

## 先预测，再打开报告

1. 记录提交号、操作系统、Python/PyTorch、Verilator 和 RISC-V GCC 版本。分别记录准备环境和实际做题的用时。有缺项时写下第一处卡点、尝试和所需提示。
2. 从 2–63 中选一个未看过结果的留出提示编号。已知投影是 16 输入、32 输出，阵列每块最多 4 行 × 4 列，提示词有 5 行，逐符号时只有 1 行。先写下两阶段预计的命令数、哪个阶段更可能受益，以及 CPU 可能最忙的计算。保留这份带时间的预测。
3. 在仓库根目录运行 `make performance GEN_SAMPLE=7`，将 7 换成你的编号。从相应 `build/performance/sample-编号/report.json` 读取自己的输入和生成结果。分别填写首个符号和后三个符号的 CPU/NPU 周期、差值、设备命令数。
4. 在 `runs.profile.npu` 里找出提示词和最后一个生成步的最大耗时项，写出各自的周期、分母和比例。任选一个单符号步骤，找出打包和设备活动各要多少拍，说明哪些成本可以相加。用 `runs.timing.cpu` 与空的 `timing/cpu-mmio.txt` 交叉核对 CPU 基线。
5. 用一小段话给出设计选择，例如只改变权重打包，或调整哪个投影先做量化。预报哪一列数字会变、怎样保持数值正确，以及什么结果会让你放弃这项改动。

**怎样验收。** 四项均需有学习者自己的证据：① 带运行前预测和可定位报告；② 完成同提示、同计时边界的四步比较，算对差值；③ 正确区分首尾计时、分段计时和设备活动，用分母支持瓶颈判断；④ 提出有数值检查与反例的下一次实验。预测与实测不一致时，能凭记录修正解释即可。环境阻塞、获得帮助与独立完成分别登记；作者运行或自动回归单独记录。
