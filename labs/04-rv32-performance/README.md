# 实验 04 · 同一台 PicoRV32，前馈投影交给谁算？

实验 03 让同一份固件在两种后端生成相同符号。这次固定 PicoRV32、模型和提示，只切换前馈升维投影的执行者。先测读入 5 个提示符号并选出第一个输出要多少拍，再逐步测输入刚生成的一个符号、直到选出 EOS 的周期。[实验 03](../03-rv32-generation/README.md) · [独立试读任务单](reader-task.md)

## 复现实验

在仓库根目录运行。需要 Python 3.10+、CPU 版 PyTorch、make、Verilator、C++ 编译器，以及支持 RV32IM/ILP32、objcopy、newlib 数学库和 libnosys 的 RISC-V 裸机工具链。全部测量在 RTL 仿真中进行，普通电脑即可完成。默认读实验 02 的 `build/projection/copy-32.pt`，缺少时 make 按原配方重训。运行器核对整个模型参数的 SHA-256 与实验 03 归档一致。

```sh
make performance
make performance GEN_SAMPLE=1
```

每个样本得到 `build/performance/sample-编号/report.json`。同目录的 `timing/` 和 `profile/` 各有一份固件、两份串口输出、设备寄存器写轨迹和 RTL 计数。可以用 `GEN_CHECKPOINT` 指定已有检查点。要从头复核，可选一组未使用过的目录，运行 `make performance PROJ_BUILD=build/repro04/model GEN_BUILD=build/repro04/soc PERF_BUILD=build/repro04/results`，会重新训练、编译并生成独立报告。[默认样本实测数据](verified-sample-0.json) · [第二个留出样本实测数据](verified-sample-1.json)

## 怎样保证两条路径可比

1. **同一台机器。** 每次从复位启动同一个 Verilator 可执行文件。PicoRV32 启用整数快速乘法、除法与桶形移位，浮点由软件库执行。32 MiB 行为 RAM、H1 分库阵列、DMA 每七拍暂停一拍的规则保持一致。测试台只在启动时提供一个只读选择值，同一计时版 ELF 分别执行两次。
2. **同一份工作。** 两端共用实验 03 的注意力、KV 缓存、量化、GELU 和贪心生成代码。纯 CPU 直接按原始权重布局做 INT8 × INT8、INT32 累加。NPU 路径真实支付分块、打包、MMIO 提交、轮询与取回的成本。两端都保留本次全部整数，使用相同的反量化、偏置与输出头。CPU 路径应有零条设备命令和零次 DMA。
3. **同一对计时边界。** 每步用两次 RV32 `rdcycle` 相减，从处理该步输入前，量到贪心选出 token 后。每步的启动准备、模型导出、复位及串口输出不在区间内。全部符号都选完后才通过串口读出本次的整数、分数和计数。两条路径分别与宿主独立量化参考比较。
4. **单独定位瓶颈。** 第二份 ELF 增加分段读数，用同一台机器再各跑一次。每步各段周期之和须等于该步总周期。驱动等待和设备运行重叠，RTL 的阵列及 DMA 周期已经包含在驱动区间内。分段读数有开销，表中的性能差取自只保留首尾读数的 `timing` 运行。[基准固件](benchmark.c) · [检查器](performance_checks.py)

## 实测成绩单

默认留出样本为 `开始 2 5 6 分隔`。两种执行方式和两种计时固件均生成 `2 → 5 → 6 → EOS`。表中差值为 CPU 周期减 NPU 周期，正值表示启用设备节省的拍数。

| 边界 | 生成的符号 | 纯 CPU 拍数 | CPU + NPU 拍数 | 节省拍数 |
| --- | --- | ---: | ---: | ---: |
| 处理 5 个提示符号 | 2 | 5,632,515 | 5,591,372 | +41,143 |
| 输入刚生成的 2 | 5 | 1,922,633 | 1,923,540 | −907 |
| 输入刚生成的 5 | 6 | 1,963,549 | 1,964,456 | −907 |
| 输入刚生成的 6 | EOS | 2,179,717 | 2,180,624 | −907 |
| **后三步合计** | | **6,065,899** | **6,068,620** | **−2,721** |

处理提示词的整步周期减少 **0.73%**。后三步合计增加 **0.045%**。换为留出样本 1 后，两端均生成 `0 → 4 → 1 → EOS`。提示词阶段为 5,584,184 / 5,543,041 拍，后三步合计为 6,132,415 / 6,135,136 拍（纯 CPU / CPU + NPU）。这些结果针对本模型、编译器、直接标量 CPU 实现和当前内存模型。

## 哪一步在等什么

- **处理提示词时，最耗时的是 CPU 的浮点 Q/K/V 投影。** NPU 路径的分段运行中，它占 2,559,643 / 5,597,492 拍（45.73%），注意力输出投影另占 15.22%。当前设备只接管前馈升维层。正式计时中，16 条设备命令从受理到写回合计 2,812 拍。
- **逐符号时，主要时间也花在 CPU 上。** 默认样本前两步最大的单项仍是 Q/K/V，占 26.56% 和 26.26%。生成 EOS 那一步，CPU 上的 GELU 升至 586,236 拍（26.85%），超过 Q/K/V 的 23.51%。两份留出提示都观察到了最后一步的这一变化。
- **为什么单符号投影没有省下整步周期？** 只剩一行激活时仍需提交 8 个输出列块。分段版每个生成步仅打包就花 14,200 拍，驱动 2,912 拍，整理返回值 1,720 拍；同阶段纯 CPU 点积为 16,397 拍。打包占这三段 NPU 路径成本的约 75%。这些读数解释了单行工作的开销来源。正式计时得出的净差为 907 拍。要验证下一项设计，可固定权重预打包后复测单行，或给 Q/K/V 建立独立量化基线后再决定是否迁移。

## 验收

| 要交付的证据 | 通过条件 |
| --- | --- |
| 身份与数值 | 全模型摘要与实验 03 一致。同一计时模式内两条路径使用相同固件和 SoC。四次运行每次核对 256 个 INT32、44 个有限 logits 和 4 个 token。整数及 token 与独立参考一致，logits 绝对误差 ≤ 0.0001，四次 RV32 输出的分数字节逐项相同。 |
| 设备活动 | CPU 全程零设备写入与事务。NPU 四步依次完成 16、8、8、8 条命令，每条均有描述符、START、CLEAR。提示词 DMA 有效读/写 1664/640 字节，随后每步 640/128 字节。 |
| 性能与诊断 | 提交每步两列整步周期、差值与输入符号；用分段版指出最大一项并给出分母。分段之和等于对应整步，禁止重复累加驱动内的设备周期。换提示后用其自身运行结果重新判断。 |
| 独立学习者 | 提交运行前预测、一次自选留出提示的报告、一个有数据支持的瓶颈和下一项可证伪的改动。记录用时、卡点与获得的提示。[任务与判分](reader-task.md) |
