# 实验 05 · 一份权重该打包几次？

实验 04 的单行前馈投影每步要发出 8 条 NPU 命令，采用现场打包的路径实测比纯 CPU 每步多用 907 拍。本实验固定同一个宽度 32 的自训练模型、PicoRV32 和 H1 4×4 阵列，只改变设备读取权重 B 的布局与生命周期。默认提示生成 `2 → 5 → 6 → EOS`。在本机仿真中，**预打包在第一个完整请求内就收回了准备成本**。[实验 04 的成绩单](../04-rv32-performance/README.md) · [样本 0 报告](verified-sample-0.json) · [样本 1 报告](verified-sample-1.json)

## 复现

在仓库根目录运行。依赖与实验 04 相同，使用 Python 3.10+、CPU PyTorch、make、Verilator、C++ 编译器和带 newlib、objcopy、nm 的 RV32IM/ILP32 裸机 GCC 工具链。

```sh
make prepack
make prepack GEN_SAMPLE=1
```

输出在 `build/prepack/sample-编号/`。报告记录了模型、固件、SoC 模拟器及原始轨迹的 SHA-256。每条路径各有串口输出、寄存器写入、DMA 计数和权重缓冲写入记录。缺少检查点时按实验 02 的原配方在 CPU 上重训。要从空目录重建，可运行 `make prepack PROJ_BUILD=build/repro05/model GEN_BUILD=build/repro05/soc PREPACK_BUILD=build/repro05/results`。每个样本编译一份 ELF，每种模式从复位运行一次，每次连续处理 3 个请求；测试台每次上限为 1.5 亿拍，宿主为每次运行设 180 秒超时。

## 三条路径怎样比较

- **纯 CPU** 直接读取原始 `W[32][16]` 做 INT8 点积。**现场打包**沿用实验 04 的内核，每条命令把 4 个输出通道的权重重排为 64 字节的小块，提交给 DMA 后复用同一临时缓冲。
- **预打包**在第一个请求到达后，由 PicoRV32 把 512 个权重字节重排成 8 个连续块，每块都是设备需要的 `[深度 16][输出 4]` 布局。固件把相应块的地址直接交给同一驱动。激活仍按相同方式打包，阵列和设备命令的形状保持一致。[基准固件](benchmark.c) · [原现场打包内核](../04-rv32-performance/projection_kernels.h)
- 每种模式使用同一个程序、同一份 RAM 初始化和 DMA 等待规则。连续三个请求使用同一提示，每次从位置零重新计算 KV 和所有输出，只让权重布局跨请求复用。另一份留出提示单独重复全套实验。
- 完整请求从处理请求、检查是否需要准备权重开始，到选出 EOS 为止；首符号延迟从同一起点到选出第一个符号为止。每步还保留实验 04 的内层边界，从处理该步输入到选出其输出。启动、训练、导出和最后的串口转储位于请求区间之外。读取的是 RV32 的 `rdcycle`。

## 周期实测

默认留出提示为 `开始 2 5 6 分隔`。下面均为整段或整步的 RTL 周期。“预打包节省”以本实验的现场打包为对照，两个重复请求分别实测，相应行的周期一致。

| 计时区间 | 纯 CPU | 现场打包 | 预打包 | 预打包节省 |
| --- | ---: | ---: | ---: | ---: |
| 首次请求到第一个符号（含准备） | 5,631,789 | 5,590,233 | 5,579,351 | 10,882 |
| 重复请求到第一个符号 | 5,631,789 | 5,590,233 | 5,564,947 | 25,286 |
| 输入 2，生成 5 | 1,922,548 | 1,923,284 | 1,910,657 | 12,627 |
| 输入 5，生成 6 | 1,963,464 | 1,964,200 | 1,951,573 | 12,627 |
| 输入 6，生成 EOS | 2,179,632 | 2,180,368 | 2,167,741 | 12,627 |
| **首次请求到 EOS，含准备** | **11,697,918** | **11,658,570** | **11,609,807** | **48,763** |
| **重复请求到 EOS，每次** | **11,697,918** | **11,658,570** | **11,595,403** | **63,167** |

**907 拍的逐步劣势已消除。** 实验 04 的单请求固件复跑仍为现场打包每步比 CPU 多 907 拍。实验 05 使用连续请求固件，三条路径在新固件内重测，现场打包比 CPU 多 736 拍，预打包比 CPU 少 11,891 拍。上表的差值全部来自同一份实验 05 固件。留出样本 1 生成 `0 → 4 → 1 → EOS`，绝对周期随输入变化，首次、重复和逐符号的相对节省在这两个样本中相同。

## 存储和回本账本

| 权重相关存储 | 现场打包 | 预打包 |
| --- | ---: | ---: |
| 原始只读 INT8 权重 | 512 B | 512 B |
| 运行需要的可写权重缓冲 | 64 B 临时块 | 512 B 常驻块 |
| 原始权重与所用缓冲合计 | 576 B | 1,024 B |

预打包新增的**工作集是 448 B**。两条路径在同一 ELF 中共享 512 B 的联合体，现场模式只用开头 64 B，因此该对照固件在所有模式下实际预留的 RAM 相同。上述账本只统计这一层权重；共同的激活、结果、串口记录及 256 B 阵列局部存储单独计。模型驻留期间，448 B 的容量代价持续存在。

**一次准备实测为 14,381 拍。** 每个重复完整请求节省 63,167 拍，按重复请求收益折算，`ceil(14,381 / 63,167) = 1` 个请求。直接查看请求的累计结果，第 1、2、3 个请求结束时分别净省 **48,763、111,930、175,097 拍**。首次与重复预打包请求的总差为 14,404 拍，其中 14,381 拍是转换内层读数，其余 23 拍来自两个计时区间之间的控制和计数开销。权重更换或缓存失效后须重新支付准备成本。

**内存总线给出了独立证据。** 现场打包每个请求将 2,560 B 写进同一个 64 B 缓冲（40 条命令 × 64 B）。预打包在第一条命令前按字节写满 512 B，之后两个请求对该缓冲均为零写入。设备的 DMA 每请求仍读 3,584 B、写 1,024 B。收益来自 CPU 避免重复重排；设备仍从系统 RAM 读取每块权重。[字节与回本检查](packing_checks.py)

## 验收与迁移

| 交付物 | 通过条件 |
| --- | --- |
| 检查点和数值 | 整个模型参数摘要与实验 04 一致。每路径、每请求核对 256 个 INT32、44 个有限 logits 和含 EOS 的 4 个符号。整数和符号匹配独立参考，logits 绝对误差 ≤ 0.0001，三条路径及重复请求的 RV32 分数位模式一致。 |
| 权重布局与设备访问 | 复核 ELF 中原始权重与缓冲符号的大小。独立转置结果与预打包的全部 512 B 相符；逐条检查总线写入的字节、时序和 B 地址。冷请求一次准备，复用时零改写。两条 NPU 路径各请求都提交 16、8、8、8 条命令，其余描述符一致。CPU 的设备活动为零。 |
| 周期与回本 | 交付首次和两次重复请求的首符号、各步与完整请求周期，把一次性准备计入首次请求。用两次重复中的最小节省计算回本数，并核对实测累计节省第一次达到零的请求编号。 |
