# 从第 257 项追到乘加器

模型给出一个形状为 5×257 的输入 X，权重 W 有 7 行，每行 257 项。学习者的任务是在每次最多归约 256 项的设备上算出 35 个输出，再解释内存预算减半以后哪一层需要改变。全章使用确定性生成的输入，在普通电脑上完成。

## 一个人的最短路线

个人挑战：先预测单条命令预算减半会影响哪些结果，再用两份存档报告检验预测，区分分块引起的命令数变化与量化引起的模型误差。

| 必修软件实验 | Python 3.10+ 运行下方参考，用宿主 C 编译器运行 `make linear` | 预测两次分块，定位布局错误，在新预算下复核输出 |

## 一次跨层计算

先预测 257 会拆成几段，再执行以下命令。第一条只依赖 Python 标准库，第二条会编译 C 标量内核并将证据存到 `build/linear/host.json`。

```sh
python3 labs/01-linear257/walkthrough.py
make linear
make linear LINEAR_BUDGET=1606
```

1. **模型与量化**。浮点参考直接按 W 的行计算各输出。激活尺度固定为 1/8，第 j 个输出通道的权重尺度为 (j+1)/16。按最近偶数舍入、限制到 [-127,127]。独立整数期望仍按 W[N,K] 读取。输入和权重有刻意设置的量化误差。
2. **编译与打包**。设备需要 B[K,N]。第 p 行第 j 列取 W[j,p]。每个任务重新打包连续 A、B，使用相同尺度。五行输入、七列输出的一条深度为 k 的命令占用 `5k + 7k + 5×7×4 = 12k+140` 字节。预算只统计该命令的 A、B、C。固件中的只读输入、合并部分和、模型权重、宿主缓冲另计。
3. **运行时与设备**。Python 和 C 分别算每段的 35 个整数。设备路线中 RV32 程序配置地址和形状，START，轮询并取回结果，然后 CLEAR。独立 RTL 测试台把同一段送进已有单 MAC，每个点积先清零。RTL 证据覆盖算术路径，矩阵控制、地址生成和总线 RTL 留在后续 SoC 实验。
4. **回到模型**。CPU 合并所有 K 段的整数，再乘两个尺度、加一次偏置。guest 输出 128×Y 的整数分子，使主机可逐项检查缩放与偏置。Python 浮点参考独立计算 Y。当前固定输入的 dyadic 值（分母为 2 的幂）与点积可在 FP32 精确表示。报告列出量化误差及每条命令打包输入的 SHA-256。

| A+B+C 预算 | K 分块 | 各段 C[0,0] | 最大命令字节 | 最终 Y[0,0] |
| --- | --- | --- | --- | --- |
| 3212 B | 256、1 | −4、−18 | 3212 | −0.546875 |
| 1606 B | 122、122、13 | 458、−670、190 | 1604 | −0.546875 |

手算基准首元素。两段合计 −22，激活和首通道权重尺度之积为 1/128，首通道偏置为 −3/8，因此 Y = −22/128 − 3/8。浮点参考为 −0.3466796875。35 项中最大绝对量化误差为 3.708984375。整数相等验收的是实现正确性。是否接受这项误差，要看应用的质量需求。

## 排错与四条执行路径

```sh
python3 labs/01-linear257/walkthrough.py --fault layout
python3 labs/01-linear257/walkthrough.py --budget 151
```

两条命令都应以非零状态退出。第一条把 W 的连续字节误当成 B，只看形状和字节数会漏过错误。检查器按原始 W 找到第一处差异 `B[0,1]=-8, W[1,0]=0`。第二条中，留给 A 和 B 的 11 字节装不下单个 K 切片所需的 12 字节。把预算调到 152，可以运行每段 1 项的软件路线。若末段整数正确而最终结果错误，检查 bias 的施加次数和跨段 scale 是否一致。

```sh
make linear-rtl
make device-test design-trial
```

后一句需要专用 QEMU 和 RV32 交叉编译器。生成的两份 `build/linear/all-*.json` 含每个后端的所有部分和、输入摘要和最终分子。设备的虚拟定时器只表达 BUSY 与完成顺序。要比较真实硬件速度，还需阵列、访存、目标时钟与端到端成本证据。

仓库附上本次运行的[原预算报告](evidence/all-3212.json)和[半预算报告](evidence/all-1606.json)。如果只有 Python，可先用下面的命令检查来源、分块摘要、四组部分和与最终数值，再操作助手。自行运行设备后，还可以用 `cmp` 逐份比较新报告和保存的报告。

```sh
python3 labs/01-linear257/connections.py handoff --interactive --reports labs/01-linear257/evidence/all-3212.json labs/01-linear257/evidence/all-1606.json
```

## 同一模型的训练与推理

```sh
python3 labs/01-linear257/connections.py training
```

训练与推理从相同的 X、W、bias 开始。用 35 个原创目标定义损失 L = Σ(Y−T)²/(2×35)。设 G=(Y−T)/35，由 Y=XWᵀ+b 可得 dW=GᵀX、dX=GW、db 按行求和。代码用中心差分抽查这三种梯度，以步长 0.001 做一次 SGD 更新。在此输入上，损失从 30.10555698 降到 29.74743374。推理只需前向的 8995 次乘加。若反向同时需要 dX 和 dW，三个矩阵乘积共 26985 次乘加，偏置、损失和更新另计。

将每个元素按 FP32 的 4 字节记账，前向同时保存 X、W、b、Y 为 12504 字节。反向复用 Y 空间存 G，保留 dX、dW、db，账本变为 24868 字节。改用动量 SGD 时，额外状态可用 7224 字节估算。脚本用宿主 Python 浮点核验数学，以上是显式张量账本，宿主进程内存另测。迁移题：若该层是输入层且无需 dX，可以删去哪项乘积与缓冲？再解释 INT8 推理时固定尺度的做法为何不能直接描述梯度下溢和微小权重更新。进一步阅读[混合精度训练原始论文](https://arxiv.org/abs/1710.03740)。

## 三项选修连接

| 场景与命令（均运行 `connections.py`） | 原理与实际观测 | 迁移验收 |
| --- | --- | --- |
| `coding` 信息与数据表示 | 同一组 32 个四值符号，定长编码 64 bit。按频率使用前缀码 0、10、110、111，编码为 56 bit，实际打包为 7 B 并逐符号解回。用 1 bit 合并相邻符号、重建为 0/2，需 32 bit，均方失真 0.375。确定性量化下 I(X;Q)=H(Q)=0.811278 bit/符号。对无损码使用三重复信道编码则需 168 bit | 解释码表和长度由双方预先约定。给一个三元组翻一位再翻两位，预测多数表决结果。比较两个码率—失真点，最优率失真曲线还需对候选编码优化 |
| `link --load 100 --phase 8 --gain 1` 物理互连 | 50 Ω 线、25 Ω 源，固定二进制序列和一阶上升沿。终端反射系数 Γ=(ZL−Z0)/(ZL+Z0)。单程 6 个采样步、每 UI 16 步，按两端反射系数乘积和往返增益叠加回波。脚本生成匹配与选定负载的两张眼图在 `build/linear/eye-*.svg`。眼高取同相位高电平最低值减低电平最高值 | 先在 50 Ω 验证零终端反射。只改采样相位，再只改衰减，解释电压裕量变化。频率无关的单程增益、固定上升沿和有限序列限定结论范围，PCIe/CXL 电气合规另验 |
| `handoff --interactive` 人机协作 | 规则助手先拿 3212 B 的旧记录回答 1606 B 的请求。用户查看引用、换用正确记录并确认，或接管终止。输入 `accept` 可观察错误依据被拦下，再用 `correct 1`、`accept` 完成纠正 | 记录首次是否发现错误、操作数、终态和用户实际耗时。脚本回放两步可达正确答案 13，真人成绩由试读采集。完成设备路线后追加 `--reports build/linear/all-3212.json build/linear/all-1606.json`，逐层追到实际提交结果 |

默认链路例子的接收眼高在 50 Ω 时为 0.639051 V，在 100 Ω 时为 0.788609 V。这个特定采样点的绝对电压开口还受负载电压幅度影响。判断信号质量时，应同时看反射系数、其他采样相位和接收门限。用 `link --load 100 --phase 0` 可观察边沿附近的开口。

## 单层设计决策记录

本例要求复用固定的量化参数和输入，35 个量化输出必须与独立整数期望逐项一致，每条设备命令占用的 A+B+C 字节不得超过预算。在满足这两个条件的方案中，选择提交次数最少者。浮点模型的任务质量、硬件速度和能耗由后续实验另行度量。

3212 B 时选 256+1。1606 B 时该方案的首条命令超出 1606 B，改选 122+122+13，峰值 1604 B。因为 2×122 小于 257，三次提交已经是这份合同下的最小值。报告中的 35 项给出数值依据。若应用另要求最大绝对量化误差不超过 1，两种方案都会因 3.708984375 的误差落选，应重新选择量化策略。这个反例区分了内存取舍与模型质量。

从新检出的工作区开始。先按实验 00 运行并解释已知向量，再完成下列任务。每人保留所用版本、平台、依赖、命令、预测、实际中间结果、原始报告、耗时、卡点和用过的提示。

| 任务 | 通过条件 |
| --- | --- |
| 解释 | 不看答案推导 12k+140，说明量化误差、整数核对和工具决策分别用什么证据判断 |
| 排错 | 指出第一处错误位于权重打包，展示修复后的 35 项一致结果，并能解释为什么多个后端可能同时接受同一份错数据 |
| 迁移 | 另选一个未演示预算，例如 2000 B。先手算每段宽度、命令数与最大占用，再重放，比较各分块之和与原方案。检查一次额外提交会改变哪些成本 |
| 整体取舍 | 从用户任务、引用版本、模型输出一路追到分块、驱动和 MAC。按内存与质量门槛筛掉不合格方案。提出一个能区分 CPU 与 NPU 成本的下一项测量，说明哪些速度和能耗结论尚缺证据 |
