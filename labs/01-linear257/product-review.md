# 第一次跨岗位评审：客户把缓冲预算减半

目标是让业务与技术岗位共同写出一页交付意见，并说明每项判断的依据。这里的客户、需求变化和评审都是教学情境。算术结果来自仓库保存的实际运行。业务岗直接读下表即可参加，技术岗可复算。[原预算报告](evidence/all-3212.json) · [半预算报告](evidence/all-1606.json)

## 发给各组的需求卡

客户希望一个 5×257 输入、7 个输出通道的 Linear 在更小的缓冲预算下运行。**第一轮**要求每条设备命令的 A、B、C 缓冲合计最多 1606 B，35 项量化输出与约定的整数参考逐项一致。客户也想知道整机每秒能生成多少 token。**第二轮**增加一条质量要求，35 项输出相对浮点参考的最大绝对误差须 ≤1。保留两轮独立决定。

| 证据 | 原预算 | 新预算 |
| --- | --- | --- |
| 命令预算 / 最大实际命令字节 | 3212 B / 3212 B | 1606 B / 1604 B |
| 分块与命令次数 | 256+1，共 2 次 | 122+122+13，共 3 次 |
| 首项部分和 / 合计 | −4、−18 / −22 | 458、−670、190 / −22 |
| 35 项整数核对 / 最大绝对量化误差 | 全部一致 / 3.708984375 | 全部一致 / 3.708984375 |

## 分工与交接

1. **产品与 FAE** 把客户的问题拆成缓冲、整数正确性、浮点质量和整机吞吐四行，注明哪轮提出、哪行缺数据。
2. **架构与编译** 写出每条命令的字节公式 `12k+140`，解释最多 122 项和为何至少要发三次命令。把配置版本交给验证。
3. **模型与验证** 对同一版本核对全部输出与误差。具体指出哪条新需求失败，给出一个需要再跑的模型实验。技术岗可在仓库根目录运行以下命令，按提示先尝试接受旧引用，再更正为资料 1 后确认。

   ```sh
   python3 labs/01-linear257/connections.py handoff --interactive --reports labs/01-linear257/evidence/all-3212.json labs/01-linear257/evidence/all-1606.json
   ```

4. **经营与项目负责人** 在限于现有功能的演示、追加质量实验、暂缓交付中选择，记录补测负责人和对排期的影响。若要估算成本，单列工时假设。
5. **客户接收人** 根据交付意见重判两轮需求。把不能复现或没有证据的指标退给具体岗位，并写明补验条件。

## 主持人核对与结业记录

第一轮可以演示这个固定算子的分块功能。1604 B 在预算内，35 个整数输出符合参考；系统总内存和整模型吞吐仍待相应测量。第二轮的误差上限为 1，两份结果的 3.708984375 均超出上限。建议由模型岗改量化或校准方案，编译与验证用同一输入复测。仅调整分块不会改变本例的量化误差。QEMU 功能结果和单 MAC 的正确性各有适用范围。[完整学生实验](README.md)

每组交一页决定记录：需求版本｜决定与适用范围｜报告及字段｜失败或缺测项｜下一步负责人及补验输入｜接收人复核。通过标准是两轮决定正确、至少一项未知指标被正确标出，且另一组能沿引用复算结论。个人轮训可把“本人已复算”与“他人复核待执行”分别填写。
